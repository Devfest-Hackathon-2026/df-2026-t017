# まなびWhy 企画 v1（2026-11-02 方向決定）

カテゴリー: **教育**
対象: **プログラミング入門に取り組む大学生・専門学生**（2026-11-02 決定）。題材は Python の基礎課題を想定
コンセプト: **答えを教えないAIチューター。ステップバイステップで過程を一緒に進め、最後に本人が「なぜ」を自分の言葉で説明できるようにする。**
背景のWhy: AIが答えを即出してくれる時代だからこそ、過程を大事にするAIに価値がある（ユーザーの言葉）。大会テーマ「Own the Why, Build with Intent」の最も直球の体現。

## 中核の流れ（1本だけ）
1. **入力**: 分からない問題・課題を入力（テキスト／写真）
2. **診断の1問**: AIは答えを伏せ、まず「どこまで分かっているか」を確かめる小さな問いを1つ出す
3. **ステップ学習**: 解法をステップに分解し、1ステップずつ「ヒント → 小問 → 本人が答える → AIが過程をチェック」。答えそのものは出さない。どうしても進めない場合は、その1ステップだけ一緒に解いて再び本人に戻す（完全拒否はしない＝挫折防止の設計判断）
4. **「なぜ」の要約**: 最後に本人が「なぜこの手順で解けるのか」を自分の言葉で書き、AIが抜けを指摘して添削する
5. **つまずきログ**: どのステップで・なぜつまずいたかを記録し、次回はその手前から復習ステップを提案する

## 通常のAIチャットとの違い（差別化）
- 違いは「答えないこと」そのものではなく、**ステップの進行管理と過程の記録**にある。チャットに頼むだけでは再現できない、状態を持った学習フロー
- つまずきログが貯まるほど、その人専用の復習になる

## 技術構成（Why付き）
- **Gemini API**: 日本語での段階的な問い生成と、過程へのフィードバックが中核。構造化出力でステップ分解をJSON管理する
- **Cloud Run**: 実行基盤。2人・5日間では運用が軽いことが理由（GKEは過剰、という比較もドキュメントに書ける）
- **Firestore**: 学習セッションとつまずきログの保存・リアルタイム性
- 採用しなかった案も記録する: 他社LLM（審査で評価されない）、答え生成型の設計（コンセプトに反する）

## 5分デモの構成（案）
1. 冒頭30秒: 「AIに聞けば答えは出ます。でも、それで学べたことになりますか？」— 実体験の問いかけ
2. デモ本編: 実際の問題で、AIが答えを出さずにステップで導き、本人が最後に「なぜ」を説明できるようになるまでを見せる
3. つまずきログの画面で「過程が見える」ことを示す
4. 締め: 技術選定のWhy（なぜGeminiか、なぜ答えを出さない設計か）を30秒で

## インタビュー計画（チームメイト主担当、11月3日実施目標）
対象: 学生5人程度。聞くこと:
1. AIに宿題や勉強を聞いて、そのまま答えを写した経験はあるか。その後どうなったか
2. 「答えは分かったのにテストで解けなかった」経験はあるか
3. 先生や先輩に教えてもらって一番役に立った教え方はどんなものだったか
4. 答えを教えてくれないAIがいたら使うか。どんな場面なら使うか
5. 自分が「なぜつまずくか」を記録してくれたら、復習に使いたいか

## リスクと対策
- 「結局ただのプロンプトでは？」という審査員の疑問 → ステップ状態管理・つまずきログ・要約添削の仕組みで答える
- 対象と科目を絞らないとデモが散る → 次の決定事項（下記）
- 答えない設計がストレスになる → ステップ単位の救済（1ステップだけ一緒に解く）を仕様に入れる

## 対象の決定（2026-11-02）
- **プログラミング入門（大学生・専門学生）に決定**。理由: 審査員がGoogleのエンジニアでコードのデモが伝わる、身近な学生へインタビューしやすい、ステップの正しさを検証しやすい
- インタビューはプログラミング版に差し替える: 「AIにコードを書かせて動いたけど、中身を説明できなかった経験はあるか」「授業の課題で、答えが分からないまま提出したことはあるか」等
- 残る小さい決定: デモで使う具体的な課題1つ（例: エラーが出たコードを、修正コードを見ずにステップで直していく課題が有力）
