- Demo Dayは1チーム6分（発表・デモ5分＋質疑1分）、Demo-first（何を・なぜ作ったか → デモ）。Regional Dayの点数は持ち越さない

## 3. 審査24点の取り方（逆算）
| 領域 | 配点 | 勝ち筋 |
|---|---|---|
| Google技術の活用 | 6点（2項目×3） | Gemini等を「中核」に。採用理由と比較した代替案を説明できること |
| プロダクトの完成度 | 9点（3項目×3） | 入力→結果→共有まで1本の流れが最後まで動く。機能を増やさず磨く。安全性（キー管理・権限）・拡張性を設計で語る |
| 社会課題への解決力 | 6点（2項目×3） | 「誰の・どんな困りごと」かを具体的に。インタビューの一次データで裏付ける |
| ピッチの構成と説明力 | 3点（1項目×3） | 実体験の冒頭 → デモ中心。Demo-first形式に合わせる |
| 採点外・必須記入 | — | AIをどこで・なぜ使ったか／学びと成長。開発中から記録しておく |

### テーマ「Own the Why, Build with Intent」の体現法
- **Whyログ（意思決定ログ）を今日から付ける**: 技術・プロダクトの判断ごとに「候補案／Pros／Cons／選んだ理由／捨てた案」を残す。そのまま提出ドキュメントの「選定理由」とピッチの材料になる。これ自体がテーマへの回答になる
- 課題設定にも根拠（インタビュー、実体験、データ）を付ける

## 4. アイデア・カテゴリーの決め方（まだ何も決まっていない前提）
5カテゴリー（医療・福祉／観光／教育／エンターテインメント／クリエイティブ）から、候補案を次の物差しで採点して決める:
1. 痛みが具体的で、本人たちの実体験・語れるストーリーがあるか
2. インタビューで裏付けを取りに行ける相手がいるか
3. Google技術（Gemini／Maps／Cloud Run／Firestore等）が「中核」になるか（後付けでないか）
4. 5分のデモで「おっ」と言わせる瞬間が作れるか
5. 2人・5日間で1本の流れを完成まで持っていける規模か

※ 観光『TabiWhy』案（卒業旅行の夜の安心プランナー）は候補の1つとして保持するが、未決定。同じ物差しで他カテゴリーの候補と比較して決める。
